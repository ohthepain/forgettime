# Live microphone capture

Forgettime has three real capture implementations: Android `AudioRecord`, iOS `AVAudioEngine`, and browser `getUserMedia` + `AudioWorklet`. The native app requires the installed `ForgettimeAudio` plugin; it never silently substitutes a browser or simulated detector. Audio is analyzed locally and is not recorded to disk or uploaded by these capture paths.

## Shared interface and clock

`src/audio/capture.ts` exports `createAudioCapture({ onFrame, onError, onStopped, onDiscontinuity }, { deviceId? })`, with `start()`, `stop()` and `setMetronome(plan | null)` methods. `onOutputError` reports output failures separately from microphone errors. `start()` must originate from a user action because browser audio activation and microphone permission require it. Once explicitly enabled, capture lets the first strong transient passing Start sensitivity establish beat 1. The shared practice controller selects single-take capture by default and releases it after a full bar of silence; its explicit Auto choice keeps the same capture listening between takes without another permission prompt. Stop, cancelled activation, and backgrounding disable Auto. No capture mode opens a microphone on app launch. A browser `onDiscontinuity` callback invalidates the entire detector/beat reference while retaining the open stream; consumers must clear their timing engine before accepting subsequent frames.

Start sensitivity is applied in the shared timing engine to the captured onset strength, for both browser and native sources. It does not alter native capture, noise rejection or quieter follow-up hit detection. Adjusting it while playing leaves the current reference intact. It applies again after the full-bar timeout or interruption; see [timing behavior](audio-validation.md) for its threshold mapping.

Each `onFrame` receives:

- `time`: **seconds** through which all capture windows have been analyzed, on the same sample clock as the onsets. This watermark can trail the capture head by less than 2.7 ms so an attack still in a partial analysis window cannot be incorrectly paused at the full-bar boundary.
- `onsets`: `{ time, strength, confidence }[]` with sample-derived attack timestamps.
- `level`, `sampleRate`, `source` (`native` or `web`) and `timestampQuality` (`hardware` or `sample-clock`).
- Optional `hardwareTime`: monotonic platform seconds for the analyzed-through sample, when the OS provides a mapping.
- Optional `waveform`: `{ time, duration, min, max }[]` of signed min/max captured PCM windows, approximately 2 ms each. `time` is each window's captured start time, not bridge arrival; it uses the same clock as detected hits. Partial windows carry across callback boundaries and are discarded across interruptions. All three capture paths use matching envelope logic. Installed native bridges currently send envelopes; raw PCM recording support is a separate adapter extension. The field is optional solely for older installed plugins; the current plugin always supplies it, including zero-valued envelopes during silence.

Deliver the onsets to `TimingEngine.addOnset()` and the analyzed-through `time` to `TimingEngine.snapshot()`. Do not use `Date.now()`, `performance.now()`, bridge arrival times, or the UI animation clock as hit timestamps. Frames continue during silence. An automatic performance pause belongs to the timing engine. The shared controller releases capture in single mode; Auto keeps it open. Explicit Stop, app backgrounding, an ended input track, an AudioContext suspension, or a native audio interruption releases the microphone and requires another Enable microphone action. Temporary browser input gaps/muting instead clear the reference and wait for fresh captured audio without reopening the device.

The score clock never rebases when hardware timestamp availability changes. Android onset times use the position of the sample read from the captured stream divided by its sample rate; `AudioRecord.getTimestamp(..., TIMEBASE_MONOTONIC)` provides the corresponding hardware clock metadata. iOS uses the input tap's `AVAudioTime.sampleTime` relative to its first captured frame, with host-time metadata when available. These clocks isolate relative timing from JavaScript callback jitter. They do not prove zero acoustic/input latency or calibrated accuracy.

The worklet transfers 1024-frame mono PCM batches with `currentFrame` timestamps to the shared TypeScript onset detector. Its output contains only synthesized metronome clicks when requested, otherwise silence. Microphone samples are never electrically monitored to the output. A delayed main-thread callback delays presentation, but does not change a captured hit's timing. Browsers do not expose a microphone hardware capture timestamp here, so the browser path is explicitly `sample-clock` quality. It requires HTTPS or localhost, microphone access and AudioWorklet support.

The browser requests `autoGainControl`, `echoCancellation` and `noiseSuppression` off. `CaptureInfo.processing` contains the applied values reported by `track.getSettings()`; unsupported/missing values remain unknown. If any are reported on, the UI suggests another input. There is no compressor, normalization or gain node in Forgettime's capture graph. Browser settings cannot establish whether hidden hardware/OS processing has altered the sound.

An empty worklet input is missing audio, not recorded silence. Empty startup quanta are ignored. If input disappears or the render-frame clock jumps after capture begins, discard any partial PCM packet, notify the timing engine immediately, and resume with the next contiguous packet's real sample timestamp. Never concatenate samples from opposite sides of a gap, fill missing capture with zeros, or change timestamps to preserve an old lock. Captured zero-valued samples remain valid silence and continue the full-bar clock. The browser input selector uses an exact device ID when chosen and displays the actual track label; unavailable selections fail visibly rather than switching to a different microphone.

## Native integration

The local `forgettime-audio` dependency supports Capacitor 8, Android API 24+, Swift Package Manager, and CocoaPods. Run `pnpm install` and `pnpm cap:sync` after changes to the plugin. `file:` packages may need reinstallation to refresh their installed native files before sync/build.

The app must declare `android.permission.RECORD_AUDIO` in its Android manifest and `NSMicrophoneUsageDescription` in its iOS `Info.plist`. No background microphone service or background audio mode is enabled. Android requests unprocessed input when supported, otherwise voice-recognition input, and attempts to disable automatic gain, echo cancellation and noise suppression. iOS uses the measurement audio-session mode. Hardware/OS processing can still vary.

Permission denial, cancelled startup, repeated starts/stops, backgrounding, interruption and input-route changes are handled explicitly. iOS validates contiguous sample positions. Android rejects capture read stalls that could overrun its recording buffer. Those native events stop capture. Browser capture clears the reference on discontinuous worklet frame positions or temporary track muting and automatically resumes listening. No new stream inherits an old beat reference.

## Detector and accuracy limits

The Android and Swift detectors are direct ports of `src/audio/onset-detector.ts`: roughly 2.7 ms RMS windows, envelope-rise detection, a slow-release level reference, 18 ms refractory period and a within-window attack crossing. The level reference rises immediately, stays held for one second after any window at least 70% of that level, then decays with a four-second time constant. The minimum candidate RMS is the greater of 0.006 and 5% of that reference. This gate operates on raw levels; it does not apply gain to samples or reported onset strength. Recovery is computed from sample duration and is independent of callback delivery.

The separate `WaveformEnvelopeCapture` is display-only and cannot influence detection or the beat clock. Its signed extrema preserve captured transient peaks. It retains only the current partial window; the UI holds a bounded one-bar envelope history (50 ms pre-roll while awaiting a reference). A renderer cadence or bridge delay can delay what is shown, but cannot move a detected marker relative to the corresponding audio. Installed native apps need a rebuilt plugin to produce these events; a shared-web update alone cannot add native waveform data.

An attack must also exceed the preceding 12 windows (about 32 ms) of background RMS by a factor of 1.8. For the 90 ms following an accepted attack that passed that full comparison, the detector can use the preceding three windows (about 8 ms) as a lower background, allowing distinct softer follow-ups after an accent has decayed. That short background cannot fall below the background measured before the accent. Follow-ups admitted only by the shorter comparison cannot extend the exception; ongoing low-frequency waveform troughs must not keep reopening it. Both comparisons retain the absolute floor, so the minimum accepted window remains at least 0.0108 RMS. The first 12 windows after capture/reset only establish background energy. There is no added lookahead or callback-time timestamping.

A monotonic decay does not retrigger the rise detector; real cymbal resonances, room reflections and other sharp ambient sounds can still produce false positives. This is a conservative initial transient detector, not drum-source separation. Very faint hits or attacks masked by recent loud audio can be missed. The noise gate depends on microphone gain and is not an acoustic loudness calibration.

Close attacks can merge below the refractory period; rolls and flams must be treated as rhythmically ambiguous by the shared matcher. Quiet ghost notes masked by cymbals may be missed. Microphone distance, clipping, Bluetooth/USB routes, gain processing, sample-clock drift and input buffering can affect results. A reported millisecond error is an estimate against a reference derived from this same recording, not a laboratory calibration or an external metronome synchronization claim. Do not use Bluetooth audio as the accuracy benchmark.

## Validation

`node --import tsx plugins/forgettime-audio/tests/validate-parity.ts` compiles the standalone Java and Swift detector implementations on the host and compares their timestamps, strengths and confidence against the TypeScript detector at 44.1 and 48 kHz. The deterministic synthesized signal includes loud/soft attacks, a close flam, a rapid roll, and a long noisy decay. This verifies port parity; it does not validate microphone hardware or detection accuracy on representative recordings.

Capture adapter/worklet tests cover stop-during-permission, duplicate lifecycle calls, backgrounding, late callbacks, missing native plugins, silent sample-frame delivery, empty startup input, mid-packet gaps, clock jumps, muted/ended tracks, selected devices and automatic reference reacquisition. A live Chromium/MacBook microphone check recovered from an observed input gap and continued until explicit Stop; this verifies capture continuity, not drum-scoring accuracy. The iOS App simulator target compiled successfully with Xcode 26.6 and code signing disabled; that confirms build integration, not device audio behavior. A full Android app build remains unverified because the Android SDK was not found; Homebrew JDK 23 is available. The shared engine tests cover musical matching and silence timing. Physical iOS/Android capture, microphone permissions, route changes, input latency and the displayed beat counter still require device testing. No drummer recordings were supplied for this implementation. Before calling the app accurate, add consented, annotated recordings with steady grooves, fills, ghost notes, flams and cymbal-heavy playing, and record false positives, missed attacks, onset error, interpretation confidence and the full-bar pause behavior at 60 and 120 BPM. See the timing validation notes for that procedure.

## Metronome output

The shared coach supplies `{ origin, bpm, fromBeat, untilTime, stopTime }` in capture-clock seconds. A quarter-note click is rendered at each eligible fixed beat, with a higher-pitched/louder accent on beat 1. The opening attack defines the clock; beat 2 is the earliest click (there is no late catch-up click for beat 1). A renewable 350 ms capture-clock lease, additionally bounded by the last hit plus four beats and the selected mode, stops future output if frame delivery stalls. Muting, changing BPM/interpretation, input gaps, stop and backgrounding clear output; hardware output already buffered can take its normal device latency to drain.

- Browser: the existing AudioWorklet renders a 25 ms decaying tone directly from `currentFrame / sampleRate`, independent of UI refresh or timer cadence. The same AudioContext handles capture and output. Before rendering, the output plan is advanced by the available input `getSettings().latency` plus `AudioContext.baseLatency` and `outputLatency` estimates. Microphone input requests the lowest available latency as an ideal constraint. No microphone-monitoring connection, compressor or echo canceller is added.
- iOS: `.playAndRecord` with `.measurement` and default speaker routing, an `AVAudioSourceNode` connected to the mixer, and the input tap/output render host timestamps map the click onto the capture timeline. Its plan is shared under a short lock, outside sample synthesis.
- Android: a native `AudioTrack` PCM thread uses output `AudioTimestamp` frame position/time and the capture `AudioRecord` monotonic timestamp mapping. It writes silence until both hardware clock mappings are available. Output failure leaves capture running.

Native `metronomeAvailable` metadata reports clock/output availability. No bridge-arrival estimate substitutes for missing native hardware timestamps; the UI reports a waiting/unavailable output. Older installed plugins reject the new method and show a rebuild notice when a click is requested. A standalone web deployment cannot upgrade native output.

**Use headphones, preferably wired.** There is no acoustic echo cancellation or source separation: a speaker click leaking into the microphone can create false attacks, false recovery or prevent the full-bar timeout. Deliberately blanking all on-beat input would erase the very drum hits being measured, so this implementation does not do that. Clock-based scheduling is not physical latency calibration: browser input buffering, native hardware offsets, Bluetooth latency and acoustic distance still need measurement on devices. No physical speaker/headphone synchronization accuracy is claimed.

API references: [Web Audio specification](https://www.w3.org/TR/webaudio-1.0/), [Apple AVAudioTime](https://developer.apple.com/documentation/avfaudio/avaudiotime), [Android AudioTimestamp](https://developer.android.com/reference/android/media/AudioTimestamp).

### Browser delay correction

Worklet input samples arrive after microphone buffering, while output samples are heard after output buffering. Without compensation, a person following the audible click appears late by approximately that combined round trip, even though the click spacing itself is sample-accurate. The original first-hit phase and every captured waveform/onset timestamp remain unchanged. Only the click's output schedule moves earlier. Subtracting a constant from every captured hit and the first-hit reference would cancel out and would not fix the issue.

`BrowserOutputAlignment` freezes the available delay estimates for each new performance reference, including silent intervals in Need help. It never estimates latency from the player's timing. A late click whose scheduling deadline has already passed is skipped rather than played immediately or truncated into an off-beat click. The musical cutoff (`stopTime`) moves earlier with the output schedule; the 350 ms watchdog (`untilTime`) stays on the render clock, so compensation greater than the watchdog interval cannot accidentally mute all output. Native playback already maps hardware host timestamps and does not receive this additional browser correction.

Missing latency fields remain unknown in `CaptureInfo.latency`; only the available estimates are summed. Browser estimates are not measured loopback calibration, especially for remote/Continuity microphones and Bluetooth. Restart listening after changing audio routes. Physical device offsets may remain and need independent measurement. The upper timing meter still waits 240 ms for rhythmic interpretation; that affects when its lines appear, not their horizontal scores or waveform hit positions.

References for the distinct delays: [Media Capture latency](https://www.w3.org/TR/mediacapture-streams/#def-constraint-latency), [Web Audio baseLatency](https://www.w3.org/TR/webaudio-1.0/#dom-audiocontext-baselatency), [Web Audio outputLatency](https://www.w3.org/TR/webaudio-1.0/#dom-audiocontext-outputlatency).

## Recorded take source contract

`CaptureFrame.pcm` is optional `{ startFrame: number, samples: Float32Array }`. `frame.sampleRate` gives its rate. `startFrame / sampleRate` uses the same absolute audio clock as `onsets[].time`; its end can lead the analyzed-through `frame.time` by a partial detector window. Browser capture delivers the actual worklet PCM, not reconstructed envelopes. Native adapters should convert bridge samples once to a Float32Array and populate the same field. Missing PCM explicitly leaves retained review unavailable; the live envelope remains usable.

`TakeRecorder` owns one continuous recording, with 50 ms of available opening context and a 120-second PCM limit. The latest finished `RecordedTake` contains `audio: { sampleRate, startFrame, samples }`, `source: 'web' | 'native'`, a continuity identity, locked `origin` in seconds, `settings: { bpm, mode, startSensitivity }`, original `onsets` and resolved `results`, and `endReason: 'silence' | 'stopped' | 'interrupted' | 'limit'`. Detector-result callbacks preserve original resolved results even after the live presentation expires. No PCM or result is synthesized for gaps.

Adapters must signal input discontinuities before delivering resumed PCM. The recorder additionally detects noncontiguous frame positions or sample-rate changes, ends the valid take, and resets continuity. Clock resets never share a take. One packet can finish an old take and begin a new one; the shared controller splits outcomes at audio-clock boundaries. The latest finished take replaces its predecessor only when another qualifying take starts. Any review action stops capture and disables Auto.

Bar navigation uses captured duration so rejected/missed hits do not hide recorded audio. Initial selection independently prefers the last complete played bar before the final accepted hit. Complete/partial describes actual PCM coverage; boundary hits belong to the following bar. The selected bar exposes its PCM slice for subsequent replay without inventing a silent tail. Audio stays in memory, never uploads, and is discarded on page/app close. Native recorded take support and loop output are not implemented by the browser-only recording slice.
