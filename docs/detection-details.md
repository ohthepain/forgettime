# Detection details and tuning

Detection details is a collapsible panel below the waveform. It shows actual attempted-attack decisions from the platform detector, including rejected candidates. Candidates are inspectable through keyboard/touch buttons and optional subdued waveform markers. Accepted hits keep their existing strength colours. The list and rejected markers share pages of 20, with explicit counts. Opening or closing the panel does not enable/disable detector instrumentation, change settings, restart playback, or affect detections.

The four controls apply when leaving their field or pressing Enter. Values are clamped to supported ranges; Reset detector defaults applies all defaults in one operation. A changed replay configuration starts exactly one fresh run from the selected source start. Subsequent loops preserve state. Live edits apply to subsequent analyzed windows while preserving detector history and the current fixed beat reference. Start sensitivity remains the independent live acquisition gate; it is not a general detection control and does not apply to established replay.

| Control | Default | Supported range | Meaning |
| --- | --- | --- | --- |
| Minimum level | 0.006 RMS | 0.001–0.1 RMS | Absolute RMS floor for the level gate and rise/contrast baselines; adaptive 5% of recent level can raise the gate. Contrast can make the effective minimum stronger still. |
| Attack contrast | 1.8 | 1.1–4 times background | Required rise above the effective background; also determines whether an accepted accent establishes the short follow-up baseline. |
| Minimum separation | 18 ms | 8–100 ms | Minimum captured interval after the previous detector-accepted attack. |
| Level recovery | 4 s | 0.25–12 s | Exponential time constant for the recent-level reference after its fixed one-second hold. This changes detection, never PCM gain. |

Defaults preserve the existing detector. The fixed minimum RMS rise remains 0.002; the rise ratio remains 1.55; rearming requires a fall below 70% of the recent peak or a rise ratio of at least 2.5. The warmup is 12 analysis windows, each approximately 2.7 ms (minimum 32 samples). These are signal-level quantities, not calibrated acoustic loudness or stick force. Updated Java and Swift ports implement this contract. While stopped, controls prepare the next run without activating audio. Starting native replay validates installed-plugin support and reports an older incompatible version instead of silently substituting the browser detector; active native capture without diagnostic support keeps the controls unavailable.

## Shared contract and retention

`src/audio/detector-contract.ts` is the canonical version-1 settings and event contract for browser, native ports, and saved-bar metadata. `DetectorSettings` contains `version`, `minimumRms`, `contrastRatio`, `minSeparationMs`, and `recoverySeconds`. `normalizeDetectorSettings` clamps supported numeric values and rejects non-finite values or unknown versions. Importers must validate serialized inputs before normalization, rather than silently repair malformed file metadata.

`DetectorCandidate` has a detector-stream-local monotonically increasing `id`, captured `time` in seconds, peak `strength`, detector `confidence`, `accepted`, applicable `reasons`, its exact `settings`, and measured levels/thresholds. Reasons are `warming-up`, `level`, `rise`, `contrast`, `rearming`, and `separation`. Several reasons can apply to one attempted attack. `elapsedMs: null` means no preceding accepted attack. A rising-envelope attempt is emitted when peak is at least 0.001, RMS rises by more than 0.0001, and RMS exceeds the previous RMS (floored at 0.0001) by at least 10%; accepted attacks are always emitted. This is an inspectable signal rise opportunity, not a claim to identify one intended drum stroke. Silence, steady levels and decays do not produce an event every window. Event generation never controls acceptance.

The shared controller adds `ReviewedCandidate.acquisition` (`started`, `below-start-level`, `low-confidence`, or `not-required`) and, when a start gate applies, `acquisitionGate: { minimumStrength, minimumConfidence }`. These preserve the distinction between detector rejection and an accepted detector attack that fails live acquisition. Rhythmic uncertainty is joined from `ResolvedHit` results for display; it does not rewrite detector acceptance. The first live reference hit is accepted but intentionally unscored.

`OnsetDetector.drainDiagnostics()` returns `{ candidates, dropped }`; undrained storage holds at most 2,048 candidates. `CaptureFrame.diagnostics` is optional: missing means unsupported/unavailable, while a supplied empty batch means supported with no attempted attacks. `RecordedTake.settings.detector` records the initial platform configuration; each retained candidate records its actual decision configuration, so live edits do not rewrite history. `RecordedTake.diagnostics` retains the first 2,048 original candidates within captured audio, plus a cumulative `dropped` count. Missing original settings or diagnostics remain missing, including old/native takes; defaults do not claim missing evidence was collected.

The live inspection buffer retains the latest 2,048 candidates and reports evictions. Replay retains candidates from the current and preceding pass, with `iteration` and `position`, capped at 2,048 and with cumulative dropped counts. `ReplayState` carries the effective settings and diagnostic count. A cap warning applies to the source take/run, not a claim that every missing event belonged to the currently selected bar. Original data remains separate from fresh replay state; changing settings does not change audio samples, BPM, phase, original results or original diagnostics. Source clocks and diagnostic timestamps never use callback arrival or UI time.

## Validation

Real PCM tests cover all rejection categories and measurements, quiet acquisition-gate failures, every supported control endpoint, reset/default equivalence, vanished replay detections with an unchanged grid, original evidence preservation, diagnostic caps, browser live changes without recapture, and packet/inspection independence. Focused UI tests verify candidate selection, applied controls, explicit source/threshold wording and an overlay toggle over real PCM-driven practice. Default TypeScript/Java/Swift onset and waveform parity passes at 44.1 and 48 kHz. These tests verify contracts and deterministic behavior; they do not establish physical-device or acoustic-kit accuracy. Actual native detector settings, diagnostics and replay are covered by host fixtures; physical device behavior remains outstanding. See [integrated validation](recorded-workflow-validation.md).
